# Избранное и темы: применение миграций вручную

Runbook для владельца проекта: всё выполняется руками в Supabase SQL Editor.

Контекст: жалоба «избранное не отображается» имела корневую причину, невидимую с
клиента. Функцию `get_favorites_overview` определяет миграция 015, и если она не
дошла до боевой базы, сервер выполняет версию из 008 с другой формой ответа. Теперь
клиент распознаёт это и бросает ошибку с названием миграции, но проверить базу и
применить файл можете только вы.

## 1. Проверка миграции 015 (сделайте первой)

Сделайте это ДО проверки избранного в приложении. Пока 015 не применена,
`get_favorites_overview()` возвращает старую форму строки, и приложение падает с
описательной ошибкой, где названа именно эта миграция, вместо тихого нуля.

Проверка, одна строка, скопируйте в SQL Editor:

```sql
SELECT * FROM get_favorites_overview();
```

Два возможных исхода, трактуйте однозначно:

- ВЕРНО: одна строка вида `{"result": {"favorites": [...], "totalUsers": N}}`.
- НЕВЕРНО: строки с колонками `match_id`, `username`, `user_id`, `total_users`,
  то есть выполняется ещё функция из миграции 008.

Если НЕВЕРНО: вставьте `src/sql/015_optimize_favorites_overview.sql` целиком в SQL
Editor, выполните, повторите проверку. Файл начинается с `DROP FUNCTION IF EXISTS
get_favorites_overview();` и затем пересоздаёт функцию, потому повторный прогон безопасен.

## 2. Миграция 022 (уже применена)

`src/sql/022_add_favorite_idempotent.sql` уже применена, поэтому раздел 3 это
повторная проверка, а не инструкция что-либо применять.

Что делает файл: `add_favorite` и `remove_favorite` теперь всегда возвращают `TRUE`
вместо `FOUND`, то есть обе операции идемпотентны. Сигнатуры функций не изменились,
поэтому `CREATE OR REPLACE` сохранил гранты. Таблица `favorites` не трогается.

## 3. Проверка идемпотентности

Подставьте свой uuid и реальный match_id, выполните по порядку:

```sql
-- подставьте свой uuid и реальный match_id
SELECT add_favorite('<ваш-uuid>', '<match_id>');
SELECT add_favorite('<ваш-uuid>', '<match_id>');   -- второй вызов не должен падать
SELECT remove_favorite('<ваш-uuid>', '<match_id>');
SELECT count(*) FROM favorites WHERE user_id = '<ваш-uuid>' AND match_id = '<match_id>';
```

Ожидаемый результат по строкам: оба вызова `add_favorite` возвращают `t`,
`remove_favorite` возвращает `t`, `count(*)` возвращает `0` после удаления, либо
`1`, если выполнить только два добавления. Свой uuid смотрите так:
`SELECT id, username FROM users;`

Почему раньше не работало. `INSERT ... ON CONFLICT DO NOTHING` оставляет переменную
PL/pgSQL `FOUND` в false, когда строка уже есть: конфликт просто пропустил вставку.
Клиент читал этот false как неудачную запись, оптимистичное обновление откатывалось,
и звезда не загоралась, хотя строка в базе была и ошибки не было видно. Зеркально то
же в `remove_favorite`: `DELETE`, затронувший ноль строк, тоже оставлял `FOUND` в false.

Фикс самой звезды миграции не требовал: `get_user_favorites` существовала в схеме с
`006_favorites.sql` и просто не имела вызывающего кода. Новое тело нужно только ради идемпотентности.

## 4. Очистка кэша

Чистить localStorage НЕ требуется: ключ кэша избранного версионирован в
`favorites_overview_v2`, персональный снимок использует `favorites_mine_v1`, поэтому
старые записи просто никогда не читаются. Для чистого листа удалите в DevTools,
Application, Local Storage, ключи `rfpl_cache:favorites_overview_v2` и `rfpl_cache:favorites_mine_v1`.

## 5. Обновление на телефоне

При `registerType: 'prompt'` (в `vite.config.ts`) уже установленное PWA продолжает
отдавать ранее прекашированную сборку, включая старый `index.html`, пока пользователь
не примет внутренний запрос обновления. Поэтому после деплоя установленное приложение
нужно открыть и обновление принять (либо удалить и поставить заново), и только потом
появятся фиксы темы и избранного. Это принятое ограничение платформы, а не дефект.
Замечание: `AGENTS.md` в разделе PWA всё ещё пишет `autoUpdate`.

## 6. Границы

Миграции применяются руками в Supabase SQL Editor, автоматического прогона нет (см.
`AGENTS.md`, раздел «SQL-миграции»). Ничто в коде не подключается к базе, чтобы
применить миграцию за вас. Строки избранного со ссылками на удалённые или
перенумерованные match_id остаются невидимыми по замыслу: их чистка была
сознательно вне объёма работ.
