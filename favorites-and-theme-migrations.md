# Избранное и темы: применение миграций вручную

Runbook для владельца проекта: всё выполняется руками в Supabase SQL Editor.

Контекст: жалоба «избранное не отображается» имела корневую причину, невидимую с
клиента: функцию `get_favorites_overview` определяет миграция 015, и если она не
дошла до боевой базы, сервер выполняет версию из 008 с другой формой ответа. Теперь
клиент распознаёт это и называет миграцию в ошибке, но проверить базу можете только вы.

## 1. Проверка миграции 015 (сделайте первой)

Сделайте это ДО проверки избранного в приложении: пока 015 не применена,
`get_favorites_overview()` возвращает старую форму строки, и приложение падает.

Проверка, одна строка, скопируйте в SQL Editor:

```sql
SELECT * FROM get_favorites_overview();
```

Два возможных исхода, трактуйте однозначно:

- ВЕРНО: одна строка вида `{"result": {"favorites": [...], "totalUsers": N}}`.
- НЕВЕРНО: строки с колонками `match_id`, `username`, `user_id`, `total_users`,
  то есть выполняется ещё функция из миграции 008.

Если НЕВЕРНО: вставьте `src/sql/015_optimize_favorites_overview.sql` целиком в SQL
Editor, выполните, повторите проверку. Файл начинается с `DROP FUNCTION IF EXISTS
get_favorites_overview();` и затем пересоздаёт функцию, потому повторный прогон безопасен.

## 2. Миграция 022 (уже применена)

`src/sql/022_add_favorite_idempotent.sql` уже применена — это ваша отчётная
информация, а раздел 3 её подтверждает: `add_favorite` и `remove_favorite` теперь
всегда возвращают `TRUE` вместо `FOUND`, то есть идемпотентны. Сигнатуры функций не
изменились, таблица не трогается, повторный прогон безопасен. Но если проверка из
раздела 3 не пройдена, действуйте по ветке «Если НЕВЕРНО» в его конце — это не
запрещено.

## 3. Проверка идемпотентности

Подставьте свой uuid и реальный match_id, выполните блок по порядку. Первая строка
сбрасывает состояние: без неё сбой миграции неотличим от остатков прошлых прогонов.

```sql
-- подставьте свой uuid и реальный match_id
DELETE FROM favorites WHERE user_id = '<ваш-uuid>' AND match_id = '<match_id>';
SELECT add_favorite('<ваш-uuid>', '<match_id>');
SELECT add_favorite('<ваш-uuid>', '<match_id>');   -- второй вызов не должен падать
SELECT remove_favorite('<ваш-uuid>', '<match_id>');
SELECT count(*) FROM favorites WHERE user_id = '<ваш-uuid>' AND match_id = '<match_id>';
```

Ожидаемый результат: оба `add_favorite` возвращают `t`, `remove_favorite` — `t`,
`count(*)` — `0`. Свой uuid: `SELECT id, username FROM users;`

Если НЕВЕРНО — любой из вызовов вернул не `t`: вставьте
`src/sql/022_add_favorite_idempotent.sql` целиком в SQL Editor (Application →
SQL Editor → New query), выполните и повторите этот блок с начала.

Если НЕВЕРНО — `count(*)` не `0`, хотя вызовы вернули `t`: функции отработали, а
состояние таблицы не то. Проверьте, что в подстановках один и тот же match_id, и
выполните блок с начала: он начинается со сброса и должен дать `0`.

Если после применения 022 всё ещё `f`, посмотрите определение (одна строка):

```sql
SELECT pg_get_functiondef('add_favorite(uuid,text)'::regprocedure);
```

В теле должно быть `RETURN TRUE`. Видите `RETURN FOUND` — в базе старая версия:
применён не тот файл либо скрипт упал до этой строки, не поймав ошибку (смотрите
вывод SQL Editor — `CREATE OR REPLACE` не применяется частично). Если `RETURN
TRUE` на месте, а вызов всё равно `f`, дело не в этой миграции: пришлите вывод.

Почему раньше не работало. `INSERT ... ON CONFLICT DO NOTHING` оставляет `FOUND` в
false, когда строка уже есть: конфликт пропустил вставку. Клиент читал false как
неудачную запись и откатывал звезду, хотя строка в базе была. В `remove_favorite`
зеркально: `DELETE` над нулём строк тоже оставлял `FOUND` в false. Фикс самой
звезды миграции не требовал.

## 4. Очистка кэша

Чистить localStorage НЕ требуется: обзор версионирован в `favorites_overview_v2`, а
персональный снимок лежит не под одним ключом, а в семействе с префиксом
`favorites_mine_v1` — у каждого свой: `rfpl_cache:favorites_mine_v1_<user-id>`, и
старые версии ключей никогда не читаются. Префикс с id добавлен намеренно: `logout()`
не чистит ни QueryClient, ни localStorage, поэтому общий ключ отдал бы следующему
пользователю на этом устройстве чужие звёздочки — из памяти до `staleTime`, с
офлайн-снимка бессрочно. Для чистого листа удалите в DevTools, Application, Local
Storage ключ `rfpl_cache:favorites_overview_v2` и ВСЕ ключи, начинающиеся с
`rfpl_cache:favorites_mine_v1`: по одному такого ключа не существует, чистить нужно
по префиксу.

## 5. Обновление на телефоне

При `registerType: 'prompt'` (в `vite.config.ts`) уже установленное PWA продолжает
отдавать ранее прекашированную сборку, включая старый `index.html`, пока пользователь
не примет внутренний запрос обновления. После деплоя установленное приложение нужно
открыть и обновление принять (либо поставить заново) — и только потом появятся фиксы
темы и избранного. Это ограничение платформы, а не дефект. Замечание: `AGENTS.md`
в разделе PWA всё ещё пишет `autoUpdate`.

## 6. Границы

Миграции применяются руками в Supabase SQL Editor, автоматического прогона нет (см.
`AGENTS.md`, раздел «SQL-миграции»). Строки избранного со ссылками на удалённые или
перенумерованные match_id остаются невидимыми по замыслу: их чистка была сознательно
вне объёма работ.
